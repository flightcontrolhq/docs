Build application artifacts directly in a Ravion pipeline. Write the source, builder, destination, and compute settings as steps, then pass the pinned artifact into deployment. Ravion's CI steps run on provisioned compute configured with an `infrastructure` block: use `build:image` for container images, `build:static` for static assets, and `custom` for tests, linters, migrations, or other shell commands.

## Write the build steps

This pipeline builds a Docker image and pushes it to ECR:

```yaml pipeline.yaml
- id: build_image
  type: build:image
  source:
    type: git
    repo: https://github.com/my-org/my-repo
    branch: main
  builder:
    type: dockerfile
  destinations:
    - id: ecr
      type: ecr
      repository_arn: arn:aws:ecr:us-east-1:123456789012:repository/my-app
  infrastructure:
    type: ec2
    instance_size: medium
```

Use `build:static` to build and upload a static site to S3:

```yaml
- id: build_site
  type: build:static
  source:
    type: git
    repo: https://github.com/my-org/my-repo
    branch: main
  builder:
    type: railpack
  destinations:
    - id: s3
      type: s3
      bucket: my-static-bucket
      region: us-east-1
  infrastructure:
    type: ec2
    instance_size: small
```

Run tests or other commands alongside those build steps with `custom`:

```yaml
- id: run_tests
  type: custom
  source:
    type: git
    repo: https://github.com/my-org/my-repo
    branch: main
  commands:
    - npm ci
    - npm test
  infrastructure:
    type: ec2
    instance_size: medium
```

## Pass the artifact to deployment

Each build step exposes outputs for the artifact it creates. `build:image` returns `build_ref`, `image_uri`, and `image_digest`; `build:static` returns `build_ref`, `s3_bucket`, `s3_directory`, and `s3_uri`. Module `build` steps also expose type-specific values such as `s3_key` for package builds. A deploy step can consume the exact image produced by `build:image`:

```yaml
- id: deploy_web_app
  name: Deploy web-app
  type: deploy
  module_instance: << pipeline.variant.id >>.web-app
  input:
    image_ref: << steps.build_image.output.image_digest >>
```

## Let a module supply the build settings

Some modules let you put build settings on the module itself. `rvn-ecs-web`, `rvn-ecs-worker`, `rvn-aws-static`, and `rvn-lambda` support module-configured build options such as the source repository, builder, Dockerfile path, and artifact destination.

When the module owns those settings, the pipeline only needs a `build` step that references the module instance:

```yaml
- id: build_web_app
  name: Build web-app
  type: build
  module_instance: << pipeline.variant.id >>.web-app
  input:
    branch: << pipeline.input.branch >>
    ref: << pipeline.input.commit >>
```

The module supplies the source, builder, and destination configuration, so you do not repeat those blocks in the step.

## Choose the artifact path

| Artifact | Documented options |
| --- | --- |
| ECS container image | Railpack, Dockerfile, or pull from an image registry |
| Static site | Railpack or Dockerfile build to S3 |
| Lambda zip package | Package build to S3, or pull from S3 |
| Lambda container image | Railpack or Dockerfile build to ECR, or pull from an ECR image registry |

Container image builds can reuse Docker layers from the destination ECR repository. Static and Lambda builds do not use registry layer cache. `nixpacks` is deprecated for pipeline CI steps.

## Build in Ravion or outside it

You can build in GitHub Actions or another CI system and hand Ravion the finished artifact:

```bash
ravion deploy create --module-instance-id <mi-id> \
  --description "Release $GITHUB_SHA" \
  --inputs '{"image_ref":"<tag-or-digest>"}'
```

There is no standalone `ravion build` command. To inspect a pipeline build, use `ravion pipeline run get <pipeline-run-id>` and `ravion logs pipeline-step <step-execution-id>`.
