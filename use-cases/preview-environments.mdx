Use separate Ravion environments to test changes before they reach production. Project config gives you a source-controlled way to create and remove named environments, while pipeline variants let one workflow target each environment.

## How it works

Create environments in your project config, then add the same module pattern to each environment that needs it. Name pipeline variants after those environment IDs so the build and deploy steps resolve to the selected environment.

<Steps>
  <Step title="Define named environments">
    Add environments such as `staging` or `review` to `ravion.yaml`. Each environment can contain its own module instances and references.
  </Step>
  <Step title="Reuse one pipeline">
    Add a variant for each environment and reference modules with `<< pipeline.variant.id >>`.
  </Step>
  <Step title="Plan changes on pull requests">
    Use the documented CI integration to plan configuration changes on every pull request. Apply after merge when the change is ready.
  </Step>
</Steps>

## Reuse a pipeline across environments

This pipeline targets whichever named environment you select when you start the run:

```yaml pipeline.yaml
variants:
  - id: production
    name: Production
  - id: staging
    name: Staging
steps:
  - id: build_web_app
    type: build
    module_instance: << pipeline.variant.id >>.web-app
  - id: deploy_web_app
    type: deploy
    module_instance: << pipeline.variant.id >>.web-app
    input:
      image_ref: << steps.build_web_app.output.image_digest >>
```

With the `staging` variant, `module_instance` resolves to `staging.web-app`. Add another named environment and variant when you need an additional place to test a change.

## Create or remove an environment from config

Project config is the documented way to manage environments and module instances. Pull the current file, edit it, preview the change, and apply it:

```bash
ravion project config pull <project-id> --file ravion.yaml
ravion project config apply <project-id> --file ravion.yaml --dry-run
ravion project config apply <project-id> --file ravion.yaml
```

Removing a module instance from the config runs a Terraform destroy plan and waits for manual approval before the instance is deleted. Treat one-off test environments as real infrastructure: review the plan and remove them when you are finished.

<Note>
  An automated per-pull-request environment workflow with teardown on merge is not documented yet. [Contact support](/contact-support) if you need that workflow.
</Note>

## Review changes before production

The [CI integration](/config-as-code/ci-integration) workflow plans Ravion configuration changes on pull requests and applies them after merge. This gives you a reviewable infrastructure diff, but a pull-request plan is not the same thing as an isolated preview environment.
