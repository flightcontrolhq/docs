Ravion lets developers work through the platform your team defines instead of learning every detail of AWS and Terraform. Versioned modules, source-controlled config, reusable pipelines, reviewable plans, and approval workflows make the paved path visible and repeatable.

## How it works

Platform teams package infrastructure patterns as module definitions and workflows as pipelines. Developers select a module, provide its inputs in project config, and use the same build and deploy workflow across environments.

<Steps>
  <Step title="Choose a module">
    Use a versioned module from the standard library or your organization's catalog. Inspect its inputs with `ravion module schema`.
  </Step>
  <Step title="Configure the project">
    Define environments, module instances, and references in `ravion.yaml`. Keep the file in source control.
  </Step>
  <Step title="Preview and ship">
    Run a dry run, review the stack plan and approval gate for infrastructure changes, then run the pipeline that builds and deploys the application.
  </Step>
</Steps>

## Start with a project config

This example gives a production environment a VPC, ECS cluster, and web service without requiring the developer to write the underlying Terraform:

```yaml ravion.yaml
project:
  givenId: demo
  name: Demo
environments:
  - givenId: production
    name: Production
    moduleInstances:
      - givenId: vpc
        type: rvn-aws-network
        version: 0.1.0
        input:
          aws_account_id: ravion-prod
          aws_region: ca-central-1
          name: demo-production
          vpc_cidr: 10.0.0.0/16
      - givenId: ecs-cluster
        type: rvn-ecs-cluster
        version: 0.1.2
        input:
          network:
            moduleGivenIdRef: vpc
          name: demo-production
          fargate_enabled: true
      - givenId: web-app
        type: rvn-ecs-web
        version: 0.5.0
        input:
          cluster:
            moduleGivenIdRef: ecs-cluster
          name: demo-production-web-app
          public_web_service_enabled: true
          build_type: dockerfile
          source_repo: my-org/my-repo
          dockerfile: Dockerfile
          container_port: 80
```

Preview and apply it with the documented workflow:

```bash
ravion project config schema
ravion module definition list
ravion module schema rvn-ecs-web
ravion project config apply <project-id> --file ravion.yaml --dry-run
ravion project config apply <project-id> --file ravion.yaml
```

## Put the workflow in source control

Pipeline config defines builds, deploys, triggers, variants, approvals, and custom CI steps. One pipeline can target production or staging through variants:

```yaml
variants:
  - id: production
    name: Production
  - id: staging
    name: Staging
steps:
  - id: build_web_app
    type: build
    module_instance: << pipeline.variant.id >>.web-app
  - id: deploy_web_app
    type: deploy
    module_instance: << pipeline.variant.id >>.web-app
    input:
      image_ref: << steps.build_web_app.output.image_digest >>
```

For infrastructure changes, the default stack workflow is plan → approval → apply. Stack runs are locked. Your platform team can replace the system pipeline with a custom pipeline that adds policy-check steps or different approval rules.

## Choose your level of automation

- **Dashboard:** inspect modules, plans, deploys, metrics, and logs.
- **CLI:** pull and apply config, start pipeline runs, inspect plans, and manage deployments.
- **CI:** plan project changes on pull requests and apply after merge.
- **API:** automate projects, environments, pipelines, deployments, and infrastructure workflows with bearer authentication.
