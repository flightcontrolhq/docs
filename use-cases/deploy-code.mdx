Author the deployment workflow in your pipeline, then let the target module carry out its configured rollout. Ravion pins the artifact, gates the release when needed, and records the deployment for inspection and recovery.

## How it works

You author the workflow from `deploy` and `rollback` module steps, `custom` CI steps, and `approval` control-flow steps. The module's deploy manager carries out the rollout using the strategy, health checks, hooks, and other settings configured on that module.

## Write the deployment workflow

This pipeline runs tests, waits for approval, and deploys the exact image produced by an earlier build:

```yaml pipeline.yaml
steps:
  - id: build_web_app
    name: Build web-app
    type: build
    module_instance: << pipeline.variant.id >>.web-app
    input:
      branch: << pipeline.input.branch >>
  - id: run_tests
    name: Run tests
    type: custom
    source:
      type: git
      repo: https://github.com/my-org/my-repo
      branch: main
    commands:
      - npm ci
      - npm test
    infrastructure:
      type: ec2
      instance_size: medium
  - id: approve_deploy
    name: Approve deploy
    type: approval
  - id: deploy_web_app
    name: Deploy web-app
    type: deploy
    module_instance: << pipeline.variant.id >>.web-app
    input:
      image_ref: << steps.build_web_app.output.image_digest >>
```

Use a `rollback` step when you need to recover a module to a specific previous deployment:

```yaml rollback-pipeline.yaml
inputs:
  - id: deployment_id
    type: string
steps:
  - id: approve_rollback
    name: Approve rollback
    type: approval
  - id: rollback_web_app
    name: Roll back web-app
    type: rollback
    module_instance: << pipeline.variant.id >>.web-app
    deployment_id: << pipeline.input.deployment_id >>
```

The `deployment_id` is the previous deployment you want to roll back to. Use `ravion deploy rollback-candidates` to list valid targets.

## Configure rollout behavior on the module

The pipeline step triggers the module's deploy manager. For `rvn-ecs-web`, the module configuration determines the rollout strategy, bake times, pause stages, approval gates, hooks, and health checks.

| Strategy | How traffic moves |
| --- | --- |
| `rolling` | ECS replaces tasks using the standard rolling deployment. This is the default. |
| `blue_green` | ECS shifts traffic between production and alternate target groups. |
| `canary` | Sends a configured percentage to the new deployment, waits through a bake time, then shifts the remaining traffic. |
| `linear` | Moves a configured percentage at each step, waiting through a bake time between steps. |

Blue/green, canary, and linear deployments can include manual approval gates and pause stages. ECS also supports optional pre-deploy and post-deploy tasks, such as database migrations. A failed pre-deploy task aborts the deployment.

Other module types use their own deploy managers:

- **EC2:** Updates Auto Scaling Group hosts in place over SSM. Container mode drains the host, replaces the app container, health-gates it, and re-registers it.
- **Lambda:** Updates code, publishes a new version, and moves the live alias.
- **Static:** Promotes a new S3 directory and can optionally invalidate CloudFront.
- **Kubernetes:** Coming soon.

## Trigger a deployment outside the pipeline

Build an artifact in an external CI provider, then trigger the module deploy manager from the CLI or REST API:

```bash
ravion deploy create --module-instance-id <mi-id> \
  --description "Release v1.4.2" \
  --inputs '{"image_ref":"<digest-pinned-image-uri>"}'
```

## Watch and recover

Ravion surfaces deploy phases, ECS task status, target-group health, and AWS infrastructure events in the dashboard. Inspect and recover deployments from the CLI:

```bash
ravion deploy get <deployment-id>
ravion deploy list --module-instance-id <mi-id>
ravion deploy rollback-candidates <deployment-id>
ravion deploy rollback <deployment-id-to-roll-back-to>
ravion deploy redeploy <deployment-id>
ravion deploy cancel <deployment-id>
ravion deploy continue <deployment-id>
```

Rollback starts a new deployment from a previous successful snapshot. Deploys are locked per module instance, so concurrent triggers queue instead of colliding.
