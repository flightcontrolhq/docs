title: "CI integration"
description: "Plan config changes on pull request and apply them on merge with GitHub Actions."

Keep your [project](/config-as-code/project-config-file) and [pipeline](/config-as-code/pipeline-config-file) config files in your repository and let GitHub Actions manage them. Open a pull request to preview the planned changes as a comment, then apply them automatically when the pull request merges.

The workflow has two jobs that cover both projects and pipelines:

- **Plan on pull request** — preview each resource's changes and post them as a comment on the PR. Projects use `config apply --dry-run`; pipelines diff the committed file against the live config.
- **Apply on merge** — run `ravion ... config apply` for each resource when the branch merges into your default branch.

## Authenticate in CI

The CLI reads a service-account API key from the `RAVION_API_KEY` environment variable.

<Steps>
  <Step title="Create a service-account API key">
    Create a service account for CI and an API key for it. See [`ravion
    service-account`](/cli/reference/service-account) and [`ravion
    api-key`](/cli/reference/api-key).
  </Step>
  <Step title="Store the key as a repository secret">
    In your GitHub repository, go to **Settings → Secrets and variables → Actions** and add a secret
    named `RAVION_API_KEY` with the API key value.
  </Step>
</Steps>

## Add the workflow

Copy the prompt below into your coding agent. It fetches the workflow template from this page, discovers your Ravion config files, reads their IDs, and adds the workflow with the `PROJECTS` and `PIPELINES` lists filled in.

<Prompt description="Discover your Ravion config files and add the CI workflow." icon="sparkles" actions={["copy", "cursor"]}>
  Add a GitHub Actions workflow to this repository that plans Ravion config changes on pull requests and applies them on merge to the default branch. Fetch the workflow template from the Ravion docs at https://docs.ravion.com/config-as-code/ci-integration and use the `.github/workflows/ravion.yml` YAML block there as-is — keep its jobs and logic unchanged, and only fill in the `env.PROJECTS` and `env.PIPELINES` lists.

To fill those lists, find every Ravion config file in the repo:

1. Search files with these extensions: `.yaml`, `.yml`, `.json`, `.jsonc`, `.cue`. The file names usually include `ravion` (project configs) or `pipeline` (pipeline configs), so prioritize those, but still confirm each by its contents below.
2. Classify each by its top-level keys (ignore everything else, such as `package.json`, CI configs, or Kubernetes manifests):
   - Project config: has a top-level `project` object AND an `environments` array whose entries contain `moduleInstances` (modules have a `type` like `rvn-...` and reference each other with `moduleGivenIdRef`).
   - Pipeline config: has top-level `steps` AND `variants` arrays (often also `triggers` and `inputs`).
3. Do NOT treat legacy Flightcontrol config files as Ravion config. Skip a file if any of these are true: it is named `flightcontrol.json`, `flightcontrol.cue`, or `flightcontrol-*.json`; it has a `$schema` pointing at `app.flightcontrol.dev`; or it has a top-level `environments` array whose entries contain `services` (with fields like `buildType`, `ci`, `region`, or `source`) and there is NO top-level `project` object. These are a different product and must be excluded.
4. Read each file's unique ID from inside the file:
   - Project: use `project.id` (a value starting with `proj_`). Do not put `project.givenId` in the workflow. If only `project.givenId` is present, look up the unique ID: if the `ravion` CLI is installed and authenticated, run `ravion project list --json` and use the `id` of the entry whose `givenId` matches. Otherwise, treat the ID as undetermined.
   - Pipeline: use the `pipe_` ID. Ravion writes it into a header comment at the top of pulled files; if the body has no ID, take it from that comment.
5. For `.jsonc` and `.cue`, account for comments when parsing. Use each file's path relative to the repo root for the `file:` value.

Populate `env.PROJECTS` with one `{ project_id, file }` entry per project config, and `env.PIPELINES` with one `{ pipeline_id, file }` entry per pipeline config. Write the workflow to `.github/workflows/ravion.yml`.

If you cannot determine the ID for a file, add the entry with a TODO placeholder and list those files so I can fill them in.

</Prompt>

Create `.github/workflows/ravion.yml`. Define your projects and pipelines once in the top-level `env.PROJECTS` and `env.PIPELINES` lists, each entry pairing a resource's unique ID (`proj_` or `pipe_`) with the path to its config file. The `matrix` job merges both lists into one matrix tagged with a `kind`, then keeps only the resources whose config file changed in the pull request or push, so a single `plan` job and a single `apply` job fan out over just the affected resources. Adding a resource is a one-line change in a single place.

The config file paths come from the env lists, so the workflow doesn't hardcode a `paths` filter under `on:` — which can't reference `env` anyway. Instead it triggers on every pull request and push to `main`, then the `matrix` job diffs the changed files against the configured paths and emits an empty matrix (skipping `plan` and `apply`) when no config file changed.

```yaml .github/workflows/ravion.yml
name: Ravion config

env:
  RAVION_API_KEY: ${{ secrets.RAVION_API_KEY }}
  PROJECTS: |
    - project_id: proj_3AV4cGr0t841Bstn4swCCrHrgly
      file: packages/web/ravion.yaml
    - project_id: proj_1CV4cGr0t841Bstn4swCCrHrgh7
      file: packages/api/ravion.yaml
  PIPELINES: |
    - pipeline_id: pipe_8Kd2mZq0t41Bstn4swCCrHrAa9
      file: packages/web/pipeline.yaml
    - pipeline_id: pipe_4Wj7nRt0t41Bstn4swCCrHrBb3
      file: packages/api/pipeline.yaml

on:
  pull_request:
  push:
    branches:
      - main

jobs:
  matrix:
    runs-on: ubuntu-latest
    outputs:
      resources: ${{ steps.list.outputs.resources }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - id: list
        env:
          BASE: ${{ github.event_name == 'pull_request' && github.event.pull_request.base.sha || github.event.before }}
          HEAD: ${{ github.sha }}
        run: |
          all=$(yq -o=json -I=0 -n '
            (env(PROJECTS)  | map({"kind": "project",  "id": .project_id,  "file": .file})) +
            (env(PIPELINES) | map({"kind": "pipeline", "id": .pipeline_id, "file": .file}))
          ')
          git diff --name-only "$BASE" "$HEAD" > changed.txt
          resources=$(jq -cn --argjson all "$all" --rawfile changed changed.txt '
            ($changed | split("\n") | map(select(length > 0))) as $files
            | $all | map(select(.file as $f | $files | index($f)))
          ')
          echo "resources=$resources" >> "$GITHUB_OUTPUT"

  plan:
    needs: matrix
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    strategy:
      fail-fast: false
      matrix:
        resource: ${{ fromJSON(needs.matrix.outputs.resources) }}
    steps:
      - uses: actions/checkout@v4

      - name: Install the Ravion CLI
        run: curl -fsSL https://github.com/flightcontrolhq/cli/releases/latest/download/install.sh | sh

      - name: Plan changes
        id: plan
        env:
          KIND: ${{ matrix.resource.kind }}
          ID: ${{ matrix.resource.id }}
          FILE: ${{ matrix.resource.file }}
        run: |
          {
            echo 'plan<<PLAN_EOF'
            if [ "$KIND" = project ]; then
              ravion project config apply "$ID" --file "$FILE" --dry-run 2>&1
            else
              ravion pipeline config pull "$ID" --file /tmp/live.yaml > /dev/null 2>&1
              git diff --no-index --no-color /tmp/live.yaml "$FILE" 2>&1 || true
            fi
            echo 'PLAN_EOF'
          } >> "$GITHUB_OUTPUT"

      - name: Comment the plan on the PR
        uses: actions/github-script@v7
        env:
          KIND: ${{ matrix.resource.kind }}
          ID: ${{ matrix.resource.id }}
          FILE: ${{ matrix.resource.file }}
        with:
          script: |
            const { KIND, ID, FILE } = process.env;
            const marker = `<!-- ravion-plan:${KIND}:${ID} -->`;
            const body = `${marker}\n## Ravion ${KIND} plan for \`${ID}\` (\`${FILE}\`)\n\n\`\`\`\n${{ toJSON(steps.plan.outputs.plan) }}\n\`\`\``;
            const { data: comments } = await github.rest.issues.listComments({
              owner: context.repo.owner,
              repo: context.repo.repo,
              issue_number: context.issue.number,
            });
            const existing = comments.find((c) => c.body.includes(marker));
            if (existing) {
              await github.rest.issues.updateComment({
                owner: context.repo.owner,
                repo: context.repo.repo,
                comment_id: existing.id,
                body,
              });
            } else {
              await github.rest.issues.createComment({
                owner: context.repo.owner,
                repo: context.repo.repo,
                issue_number: context.issue.number,
                body,
              });
            }

  apply:
    needs: matrix
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    permissions:
      contents: read
    strategy:
      fail-fast: false
      matrix:
        resource: ${{ fromJSON(needs.matrix.outputs.resources) }}
    steps:
      - uses: actions/checkout@v4

      - name: Install the Ravion CLI
        run: curl -fsSL https://github.com/flightcontrolhq/cli/releases/latest/download/install.sh | sh

      - name: Apply changes
        env:
          KIND: ${{ matrix.resource.kind }}
          ID: ${{ matrix.resource.id }}
          FILE: ${{ matrix.resource.file }}
        run: |
          if [ "$KIND" = project ]; then
            ravion project config apply "$ID" --file "$FILE" --autoapprove
          else
            ravion pipeline config apply "$ID" --file "$FILE"
          fi
```

<Warning>
  Project apply uses `--autoapprove` to approve supported stack change pipeline runs without a
  manual gate. Removing a module instance still runs a Terraform destroy. Drop `--autoapprove` if
  you want a human to approve runs in the Ravion dashboard.
</Warning>

<Note>
  Pipeline config apply has no `--dry-run` or `--autoapprove`, and applying creates a new pipeline
  version every time. For pipelines, the plan step instead pulls the live config and posts a `git
  diff` against the committed file so you can preview drift before merging.
</Note>
